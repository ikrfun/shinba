# Design workshop

Help the person make and record design decisions. Do not decide on their behalf, invent requirements, or treat filled fields as proof of a sound design. Respect existing project constraints and scale the exercise to the problem; mark irrelevant topics as not applicable with a reason.

1. Inspect relevant project instructions and implementation before making claims. Ask about the goal, actors, constraints, and uncertain decisions; work in small batches.
2. When a worksheet is wanted, copy `assets/workshop.html` into a suitable project-local location and tell the user how to open it. It works offline; browser storage is local and is not a shared project document. The explorer can show a folder that the user selects in the browser; it does not automatically know the agent workspace or persist folder access, and it reads files without editing them. Ask the user to export JSON and share its path or contents when collaboration with the agent is needed. Never assume the agent can see browser storage. Do not overwrite existing files without permission.
3. Guide the user through use cases and variants, information and invariants, sequence flows, API contracts where applicable, architecture alternatives, infrastructure failure modes, boundaries, interfaces and models, technology choices, and tests. Revisit earlier decisions when a later constraint changes them. Use `references/facilitation.md` as appropriate. For board collaboration, case execution and sample implementations, follow `references/board-collaboration.md`. For design review, inspect the relevant code and use `references/design-review.md` to choose evidence-backed questions. Do not force HTTP, onion layers, or a particular platform on projects where they do not fit.
4. Present alternatives with context-specific benefits, costs, failure modes, and evidence that would distinguish them. Explain unfamiliar terms with a concrete example. Separate known facts, assumptions, open questions, and decisions; label illustrative examples. Verify version-sensitive technology or platform claims against current primary documentation.
5. Keep the human responsible for selecting tradeoffs. Record rationale, rejected options, and unresolved questions. Derive tests from normal and exceptional cases, including expected outcomes and relevant boundaries. At handoff, summarize decisions, unresolved risks, and next actions; do not imply completeness from worksheet progress.

The worksheet is a multi-board visual workspace with movable cards, directed connections and local images. It exports JSON for sharing and continued editing; version 1 worksheet JSON can be imported as cards. Ask for an exported file before interpreting the board; the agent cannot read browser storage. Read card titles, bodies, types, storage fields (location, path and contents), and links together as a graph, and inspect embedded images if needed. Discuss one small piece at a time: ask the learner to explain their reasoning, offer a hint or a concrete comparison when useful, and distinguish a proposed example from a decision. Do not promise that a completed design eliminates all unexplained behavior; use review and tests to find gaps. Avoid recording secrets or personal data without an explicit need.
