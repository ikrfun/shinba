# BoardとCardの操作・CLI設計案

検討中の案。一部は実装済みで、現在の操作方法とデータの扱いは [Board と CLI の使い方](board-cli.md) を参照する。以下の未決定事項は、この案を作った時点の記録として残す。Gitのコミットと、ここでいうボードへの保存は別の操作とする。

## 目的

人とAIがカードを使って設計を整理し、内容と関係を参照・変更できるようにする。AIの一連の変更を確認してから明示的に保存し、shinbaの画面にも反映する。画面上の未保存変更や、別の編集者による変更を失わない。

## ユースケース

| 操作 | 表現したいこと | CLIでの操作案 |
| --- | --- | --- |
| カードを追加する | 課題、要求、案、判断、仕様、検証結果などを記録する | `card add --title ... --body ...` |
| カードを読む | 目的のカードと、その前後の文脈を確認する | `card show <id>`、`card list`、`card related <id>` |
| 内容を更新する | 既存の説明や決定事項を修正する | `card update <id> --body ...` |
| 親子に整理する | 複数のカードを一つの話題にまとめる | `card move <id> --parent <id>` |
| 関係を表す | カード間の関連と方向を記録する | `card connect <from-id> <to-id>` |
| コードに結びつける | カードとコードのシンボルを対応づける | `card link-symbol <id> ...` |
| 見た目を調整する | 位置、サイズ、重なり順を変える | `card layout <id> ...` |
| カードを削除する | 不要なカードを取り除く | `card delete <id>` |

コマンドは例であり、実装済みの機能ではない。関係の種類や方向、カードの種類を固定するかは未決定。カード間の線とコードへのリンクは別の関係として扱う案。削除時の子カードや接続の扱いは決める必要がある。

## 作業と保存

画面とCLIはそれぞれ独立した作業コピーを持つ。画面では、ノーマルモードの `i` で編集を開始したときに、その時点の保存済みボードを基準として保持する。変更は作業コピーに自動保存し、共有ボードへの反映は `:w` で行う。`:w` はCLIと同じ保存処理を呼び、保存済みのボード、編集開始時の基準、作業コピーを比較する。画面での移動や接続など、本文編集以外の変更も作業コピーに含める。閲覧モードではテキストを直接編集せず、テキスト上からのドラッグもカードの移動として扱う。

AIの保存成功後、画面に未保存の変更がなければ保存結果を表示する。画面に作業コピーがある場合は、その内容を破棄したり無条件に再読み込みしたりしない。外部の更新を知らせ、保存時に三者比較する。競合する場合は双方の値と基準を表示し、選択または編集による解消を経て再度保存する。解消中にも保存済みボードが変わり得るため、再保存時に比較し直す。

アプリ終了やプロジェクトの切り替え時は未保存の作業コピーを復元できるようにする。保存失敗時も作業コピーを残し、失敗の表示から再試行や競合解消に進めるようにする。保存の通知が届かない場合に備え、画面を開き直したときや保存前にも保存済み状態を確認する。

1. agentは対象のボードと、変更の基準となる状態を取得する。
2. カードの追加や更新を作業中の変更として記録する。保存済みのボードはこの時点では更新しない。
3. 変更内容と基準からの差分を確認する。
4. `board save` のような明示操作で、一連の変更を保存する。成功後、開いているshinbaへ更新を通知する。
5. 画面側は保存結果を読み込み、未保存変更がなければ反映する。未保存変更があれば差分を照合し、競合しない変更を統合する案。

作業中の変更の保存先、複数のagentが並行作業するときの識別方法、プロセス終了後の再開と破棄の方法は未決定。コマンドをまたいで変更を保持できることが必要。通知の配送方法と、shinbaが開いていない場合や通知に失敗した場合の再読込方法も決める。

## 競合の検出と解消

保存時に、作業の基準・作業中の変更・現在の保存済み状態を比較する。異なる箇所の変更は統合を試み、同じ箇所の異なる変更、削除と編集の重複などは競合として返す案。位置と本文のように対象が異なる変更をどう判定するかも定める。

競合がある場合は保存せず、対象、基準、両者の値を提示する。agentまたは人が内容を確認して修正し、再度保存を試みる。画面の未保存変更との競合では、両方の内容と差分を表示し、どちらを残すか、編集して解消するか選べるようにする案。自動解決できる範囲と、判断を人に求める条件は未決定。

競合を確認した後に保存済み状態がさらに変わることもあるため、保存直前に再確認する。保存の途中で失敗した場合に、一部だけが反映された状態にならない方法を検討する。通知は保存の成功後に行い、通知だけで保存成功とみなさない。

## データ構造との関係

カードの本文・関係などの意味情報と、位置・サイズなどの表示情報を分けて保存する案を検討する。AIは必要な内容と関連カードだけを取得でき、表示情報が必要なときはIDで参照する。分割の粒度、親子関係の位置づけ、整合性、既存JSONからの移行方法は未決定。CLIと画面は共通の操作規格に従う案とし、画面の選択状態や表示範囲などは画面側で解決する。

## 先に決めること

- 最初に扱うユースケースと、カードが表す情報・関係の範囲。
- 作業中の変更の保存場所、識別方法、有効期間と破棄方法。
- 競合の単位と自動統合できる条件。削除、親子、接続、位置も含む。
- 保存と画面への通知の方法。外部ツールによる直接編集も検出するか。
- CLIが返す差分・エラーの形式と、agentと人の確認・解消手順。
- 既存の自動保存、revision、保存済みボードとの互換性と移行。

## 確認するケース

通常の追加・更新・接続、異なるカードへの同時編集、同じ本文の同時編集、削除と編集の競合、画面上の移動と本文更新、保存途中の失敗、再試行中の再変更、通知失敗、アプリ未起動時の保存、既存ボードの移行を確認する。
