# ビジュアル設計と coding agent を組み合わせたコードエディター

## コンセプト

ビジネス要件の検討から設計、コーディング、テストまでを、ビジュアルに行き来しながら進めるコードエディターです。

人が要件を精査し、設計やコードの意味を理解したうえで判断することを中心に置きます。coding agent は実装の代行だけでなく、検討の抜けを問いかけ、必要な知識や参考実装を示し、人が自分で考える作業を支えます。

特に、アーキテクチャやレビューの経験がまだ少ないエンジニアが、agent に作業を任せきりにせず、設計と実装を学びながら開発することを想定しています。

## 解決したい課題

coding agent に要件や実装をまとめて任せると、コードは得られても、なぜその設計になったのか、
どのケースに対応しているのかを追いにくくなることがあります。知識が不足している段階では、agent が出した設計の妥当性や、見落とした例外を判断することも簡単ではありません。

一方、要件、処理の流れ、データ、コード、テストを別々に検討すると、それぞれの関係を追う負担が生じます。このエディターでは、それらを関連づけて可視化し、人が判断した理由と未決事項を残せるようにします。
一定数のエンジニアがホワイトボードや紙、miroといったツールで視覚的に情報を整理してから、それをドキュメントに起こしてcodingを行うことがありますが、本ツールではそれらの作業からコーディングまでをシームレスにつなげる体験を提供します。

## 利用者と agent の役割

利用者は、解決したい課題や業務上の条件を示し、選択肢の違いを考え、要件と設計を判断します。実装やテストの結果も確認し、自分の言葉で説明できる状態を目指します。

coding agent は、利用者が示した情報と実際の codebase を読み、必要な問い、知識、参考例、実装案を提示します。既存の実装から分かる事実と推測を分け、未確認の前提を決定済みとして扱いません。利用者の判断が必要な点は、判断の材料とともに示します。

agent に実装やテストを依頼する場合も、何を試したか、何が起きたか、どこまで確認できたかを利用者が追えるようにします。

## 想定する開発の流れ

1. **業務要件とユースケースを整理する。** 誰が何をしたいか、何が成功か、事前条件や対象外は何かを明確にします。agent は不足していそうなケースを候補として示します。
2. **ケースごとの動作を考える。** 通常、代替、失敗などの流れを分け、入力、出力、状態の変化を整理します。
3. **データと処理を設計する。** schema、シーケンス図、保存先、外部サービス、例外とその対策を検討します。
4. **アーキテクチャとコード構成を考える。** 複数の構成を比較し、適用する理由と見送る理由を記録します。フォルダ、ファイル、クラス、インターフェース、関数の関係を表現します。
5. **実装とテストを進める。** ケースからテストを考え、入力、実行前の状態、期待結果と実際の結果を照らし合わせます。設計とコードを見比べ、必要に応じて前の段階へ戻ります。

この順序は考え始めるための流れです。設計中に新しい制約や疑問が見つかった場合は、前の段階を見直します。

## 主な要件

### 1. ビジュアルに設計できる

利用者は、複数のボードを使い、ケース、処理、入力、出力、メモ、判断事項、保存先などを配置できます。ケース整理、schema、処理の流れなどを別のボードで扱い、それぞれの関係を追えるようにします。

カード同士の接続、処理の入れ子、複数選択と移動、拡大・縮小を通じて、考えた構造を整理できます。画像やメモを、関連する処理の近くに置けるようにします。シーケンス図など、処理の順序や分岐を表す手段も必要です。

### 2. 要件・設計・コードを結びつける

ユースケース、データ形式、処理、例外、テスト、コードの対応を利用者が追えるようにします。業務上の条件が、どの処理やテストで扱われるかを確かめられることが必要です。

コード構成は、フォルダとファイルに加え、ファイル内のクラス、インターフェース、関数などを表現できるようにします。設計中の構成と、実際の codebase に存在する構成は区別します。

### 3. 知識と参考実装を必要な場面で示す

coding agent は、利用者が検討している処理や設計に応じて、関連する知識、選択肢、利点と欠点、考えるための問いを示します。クリーンアーキテクチャやオニオン構造などは候補として比較し、採用を前提にはしません。

参考用のリポジトリを指定できるようにし、agent が関連する実装や設計を探して、出典とともにボードへ示せるようにします。参考実装の動作と、今回の設計への適用案は区別します。

### 4. codebase に基づいてレビューする

agent は、設計をレビューする前に、関連する実装、設定、テスト、運用上の前提を確認します。確認できた内容を根拠として示し、確認できない条件は質問または仮定として扱います。

レビュー観点には、冪等性、再試行の可否、コスト、処理時間、複数の実行単位からの同時アクセス、停止や入れ替え時の挙動などを含めます。複数 pod のような具体的な前提は、実際の構成や利用者が示した条件を確かめたうえで扱います。

### 5. ケースを定義し、結果を確かめる

処理に関連するテストケースを定義し、入力、実行前の状態、期待する応答、実行後の状態を記録できるようにします。例えば、画像を新規にアップロードするケースと、同じ画像がすでにあるケースを分けて検討します。

実行結果には、観測した応答や状態に加え、実装コード、テスト用の代替、実際の外部サービスのどれを使ったかを示します。未実行の想定を、実行済みの結果として扱いません。

### 6. 人と agent が同じ作業内容を扱う

利用者が編集中のボードを agent が読み、フィードバックや実行結果を関連する場所に返せるようにします。手作業での JSON の受け渡しを減らし、設計の流れを中断せずにやり取りできることが目標です。

人と agent が同時に変更する場合は、互いの変更を意図せず失わない扱いが必要です。agent が新しい提案を出したことと、利用者がそれを採用したことも区別します。

### 7. 設計判断を残す

確定した要件、採用した案、その理由、見送った案、未確認事項を区別して記録します。後から設計を見直すときに、何を前提に判断したかを追えるようにします。

## 現時点の方針と未決事項

デスクトップアプリの基盤は、現時点では Electron を選ぶ方針です。Rust の学習は今回の優先事項にしていません。

coding agent との連携には MCP を候補としていますが、具体的な接続方法や保存方式は未決定です。どの coding agent をどのように起動・接続するか、ボードからの依頼と既存の会話からの依頼をどう扱うかも、ユースケースを整理してから決めます。

コードエディターとして扱う編集機能の範囲、設計とコードの対応づけ方、テストの実行環境、参考リポジトリの扱い、最初に実現する範囲も今後の検討事項です。
